## C1 — `config.json` 明文存放真实注册码（P0）

**问题**：`config.json` 里 `reg_code` 字段明文写着真实注册码
（40 位十六进制串，本文档不再复现其原文以免二次泄露），且该文件与项目一起存放。

**为什么是问题**：
- 注册码是**付费凭据**，泄露等于把授权让给别人用；
- 一旦项目进 git / 打包 / 发给同事，凭据就永久外泄（即使之后删掉，历史提交里仍在）；
- 同样的问题也存在于同期另一个工程的 `main.cpp`（硬编码在源码里，更严重）。

**修改内容**：
1. `config.json`：`reg_code` 清空为 `""`，并写入 `_reg_code说明` 指引；
2. 新增 `run_server.py::resolve_reg_code()`，注册码支持三种来源，优先级：
   `--reg-code` 参数 > 环境变量 `DM_REG_CODE` / `DM_MCP_REG_CODE` > `config.json:reg_code`；
3. 启动日志只打印"已提供（来源：…）"或"未提供"，**不打印注册码本身**；
4. 新增 `.gitignore`，排除 `config.json` / `*.log` / `python32/` / `__pycache__/`。

**验证**：
```bash
# 环境变量优先级生效
DM_REG_CODE=deadbeef python -c "from run_server import *; print(resolve_reg_code(None, load_config()))"
# -> ('deadbeef', '环境变量 DM_REG_CODE')
```

**待确认**：同期另一个工程 `main.cpp` 里的硬编码注册码如何处理（属该工程自己的整改项）。

## C2 — `run_server.py` 死参数 + 配置语义缺陷（P1）

**问题一：死参数**。`--load-guard-on-start` 在第 86 行定义，但 `main()` 全文从未引用它。
用户传了它**没有任何效果**，却会以为"已开启启动加载盾"。

**问题二：配置键污染**。`load_config()` 直接把 JSON 全量返回。而
`config.example.json` 里用 `_说明` / `_dm_path说明` 等**下划线前缀键**写字段说明 ——
这些"文档键"会被一并读进 `cfg`，若将来有人写 `cfg.get("_说明")` 就会拿到说明文字而非配置。

**修改内容**：
1. 删除 `--load-guard-on-start`（其语义已由默认 `guard=True` 覆盖，真正要"不加载盾"应该用 `--no-guard`）；
2. `load_config()` 增加：非 dict 顶层 → 记日志返回 `{}`；`_` 前缀键 → 过滤掉；
3. `--no-guard` 帮助文案补上后果说明（"内存接口将全部被拒绝"）。

**验证**：
```bash
python run_server.py --help | grep load-guard    # -> 无输出（已删除）
python -c "from run_server import load_config; print([k for k in load_config() if k.startswith('_')])"
# -> []（下划线键已过滤）
```

## C3 — HTTP 状态码恒为 200（P1）

**问题**：`server.py` 中

```python
return self._send(payload, 200 if not res.get("isError") else 200)
```

三元表达式的两个分支都是 `200`，条件判断完全无效 —— 典型的"写了但没生效"。

**为什么是问题**（这里有个反直觉的点，值得团队记住）：
- **不能**简单地改成 `isError -> 500`。因为工具级错误（如 `DM_GUARD_NOT_LOADED`）
  是本服务的**正常业务结果**，不是传输层故障；
- 若返回 4xx/5xx，Python 的 `urllib.request.urlopen()` 会抛 `HTTPError`，
  脚本客户端**拿不到结构化的错误体**，反而更难排错；
- 真正该用 4xx 的是"调用方明显用错接口"，即 `DM_UNKNOWN_TOOL`。

**修改内容**：显式区分三种情况，并把判断逻辑写进 docstring：

| 情况 | 状态码 | 说明 |
|---|---|---|
| 工具执行成功 | 200 | 正常 |
| 工具执行失败（有结构化错误体） | 200 | 业务错误，body 里 `ok=false` |
| 未知工具名 | 400 | 调用方用错了接口 |
| 请求体超限（见 C9） | 413 | 传输层问题 |

**验证**（实测输出）：
```
health      -> 200
unknown tool-> 400  DM_UNKNOWN_TOOL
dm_read_int -> 200 | error=DM_NOT_LOADED   （未加载 DM 时的业务错误，仍是 200）
```

## C4 — `auto_bind` 宽松匹配可能误绑窗口（P1）

**问题**：`auto_bind` 的查找回退链里，第 4~6 步是宽松匹配：

```python
FindWindowByProcess(module, "")   # 只给进程名
FindWindow("", title)              # 只给标题
FindWindow(class, "")              # 只给类名
```

**任一命中就直接 `bind_window`**，从不复核。

**为什么是问题**：
- `FindWindow(class, "")` 会绑到**任意**一个 `UnrealWindow` 类的窗口（其他 UE 游戏也是这个类名！）；
- `FindWindow("", title)` 只要标题里含"剑灵"就行，而**浏览器标签页、记事本、聊天窗口**
  标题都可能含这两个字；
- 项目文档（README / docs）明确承诺"严格匹配 `class=UnrealWindow` + 标题含《剑灵》"，
  **代码实现与文档承诺不一致**；
- 误绑后果严重：后续所有 `read_*` / `write_*` 都会作用在**错误的进程**上，
  而 `DmGuard` 已加载的情况下，写错进程可能造成第三方程序崩溃。

**修改内容**：
1. 新增 `DmCore._verify_target_window(hwnd, window_class, window_title)`：
   - `GetClassName(hwnd)` 必须**完全等于** `window_class`（大小写敏感，`UnrealWindow` 是引擎固定类名）；
   - `GetWindowTitle(hwnd)` 必须**包含** `window_title`（用包含而非相等，兼容标题里的版本号/区服后缀）；
   - 返回 `(ok, detail)`，`detail` 记录实际读到的类名/标题，便于定位为何被拒。
2. `auto_bind` 的候选改为三元组 `(label, fn, need_verify)`：
   - 只有**显式传入的 hwnd** 跳过复核（调用方已明确指定目标）；
   - 其余所有候选命中后**必须**过复核，不通过则**继续尝试下一个候选**；
   - 每一步的复核结果写进 `info["steps"]`，全部失败时返回明确错误而非静默误绑。
3. 失败提示改为说明"未找到**通过复核的**窗口，要求类名 == X 且标题包含 Y"。

**验证**：复核逻辑的单元行为可在游戏未运行时通过 mock `_call` 验证；
实机验证需游戏运行，见《疑问与待确认事项.md》Q3。

**兼容性说明**：显式 `dm_bind_window(hwnd=...)` 工具**不受影响**（那是用户明确指定目标，
不属于"自动查找"，本就不该复核）。

## C6 — `tools.py` 的 `REQUIRES` 死代码（P2）

**问题**：`REQUIRES` 字典（20 行）声明了每个工具的前置条件，但全文
**没有任何一处引用它**。真正的前置校验在 `core.py` 的
`_ensure_loaded()` / `_ensure_guard()` / `_target()` 里。

**为什么是问题**（这是最值得警惕的一类技术债）：
- 两份"前置条件"描述并存 → 必然漂移。实测核对发现 `REQUIRES` 里
  `dm_get_module_base_addr: []`（声称无需 loaded），但实现里它**调用了**
  `self._ensure_loaded()`；
- 更糟的是读者会以为"改 `REQUIRES` 就能控制权限"，改完毫无效果；
- 46 个工具的注册表 + 46 条 lambda 处理器，**没有一致性校验**，
  漏一条只会在该工具被调用时才报 `未实现处理器`。

**修改内容**：
1. 删除 `REQUIRES`，改为一段注释，**明确指出唯一事实来源是 `core.py` 的
   `_ensure_*` 执行路径**，并记录核对结论：「46 个工具中没有任何一个能在 DM 未加载时成功执行」；
2. 新增 `_self_check()`，在**模块导入时**校验：
   - `TOOL_INDEX` 与 `HANDLERS` 的键集合必须完全一致（缺/多都报错）；
   - `WRITE_TOOLS` 中不能出现未声明的工具名；
3. `WRITE_TOOLS` 由可变 `set` 改为 `frozenset`（常量语义，防误改）；
4. `call_tool()` 补 docstring，说明"前置条件不在本层判断"。

**验证**：
```bash
python -c "from dm_mcp import tools; print(len(tools.TOOLS), len(tools.HANDLERS))"
# -> 46 46，且导入即自检
```

**设计取舍**：我没有把 `_self_check()` 做成"运行时校验 `REQUIRES` 与 `_ensure_*` 一致"，
因为 Python 无法可靠地静态分析方法调用图；强行做只会引入脆弱的手工映射表 —— 那正是
`REQUIRES` 失败的原因。改用"导入期校验注册表/处理器对齐"这个**能真正保证**的约束。

## C9 — HTTP 无请求体上限（P2，安全加固）

**问题**：`_body()` 直接 `self.rfile.read(int(Content-Length))`，无上限。
HTTP 模式是**单线程** HTTPServer（为保 STA 公寓，见 docs/01 第 3.4 节），
一个超大 body 就能把服务卡死 —— 这是单线程架构下必须补的防护。

**修改内容**：
1. 新增模块常量 `MAX_BODY_BYTES = 1 << 20`（1 MiB；工具入参是地址/数值/短字符串，正常远小于此）；
2. `_body()`：非法 `Content-Length` 容错为 0；超限返回 `{"_too_large": length}`；
3. `do_POST()`：检测到超限返回 **413 REQUEST_TOO_LARGE** + 实际长度。

**验证**：
```
超大 body -> 413 REQUEST_TOO_LARGE   （实测 2 MiB body）
health    -> 200 True                （正常请求不受影响）
```
