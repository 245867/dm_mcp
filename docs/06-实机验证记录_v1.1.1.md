## D1 / D2 — 未注册时原生接口触发进程级崩溃（P0）

### 现象

在**未注册**（无注册码，或注册码无效）状态下调用以下接口：

```
DmCore(...).load()          -> 内部走 guard() -> DmGuard
DmCore(...).guard(True)     -> DmGuard
DmCore(...).bind_window(h)  -> BindWindowEx
```

全部抛出：

```
OSError: exception: access violation reading 0x00000000
```

### 为什么这是 P0（最严重）

- 这**不是** DM 返回的错误码，而是 **Windows 访问违例 —— 进程直接崩溃**。
  Python 的 `try/except` **完全兜不住**：进程已经没了，异常处理代码根本没机会执行。
- 对 MCP 服务意味着：**一次调用就把整个服务打死**，客户端只看到连接断开，
  拿不到任何可读错误，排查成本极高。
- 触发门槛极低：用户只要没配注册码（默认状态！），调 `dm_load` 就会崩。

### 根因

未注册的 DM 内部某些指针未初始化（为空），而 `DmGuard` / `BindWindow` 会直接解引用。
DM 自己没做空指针检查，我们也不能指望它做。

**关键认知：对这类问题，"优雅地捕获异常"是错误的方向 —— 异常根本来不及抛。
唯一正确的做法是在调用前就判断出"现在不能调"，从源头不调用。**

### 修复

新增预检闸门 `DmCore._ensure_reg_for_native(what)`：

```python
def _ensure_reg_for_native(self, what):
    """调用“未注册时会硬崩”的 DM 原生接口前的预检。"""
    if self._reg_ok is True:
        return
    if self._reg_ok is None:
        raise E.DmMcpError(E.NOT_REGISTERED,
            "未提供注册码，无法%s（已阻止一次会导致进程崩溃的原生调用）" % what, ...)
    raise E.DmMcpError(E.NOT_REGISTERED,
        "注册失败（Reg != 1），无法%s（已阻止一次会导致进程崩溃的原生调用）" % what, ...)
```

接入点：
1. `load(guard=True)`：未注册/注册失败时**跳过** `guard()`，在 `guard_detail` 里标注
   `action="skipped-unregistered"` 或 `"skipped-reg-failed"`，并写入 `notes`；
2. `guard()`：入口处调用预检（覆盖用户直接调 `dm_guard` 的情况）；
3. `bind_window()`：入口处调用预检（覆盖 `dm_bind_window` 与 `auto_bind` 内部调用）；
4. `auto_bind()`：捕获后给出**针对性提示**（区分"找不到窗口"与"未注册无法绑定"）。

### 修复前后对比

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `dm_load`（无注册码） | 💥 进程崩溃 | ✅ 返回 status，`guard_loaded:false` + 可读 notes |
| `dm_guard`（无注册码） | 💥 进程崩溃 | ✅ `DM_NOT_REGISTERED` + hint |
| `dm_bind_window`（无注册码） | 💥 进程崩溃 | ✅ `DM_NOT_REGISTERED` + hint |
| `dm_auto_bind`（无注册码） | 💥 进程崩溃 | ✅ `ok:false, error:DM_NOT_REGISTERED`，且**仍能报出找到的 hwnd** |

## D3 — `GetClassName` 不存在，导致窗口类名校验失效（P1）

### 现象

调用 `dm_get_class_name` 返回：

```
DM_NOT_SUPPORTED: COM 对象（ProgID=dm.dmsoft）不支持方法 GetClassName
```

### 为什么这是 P1（这个最阴险）

窗口类名校验是**防止误绑的最后一道闸门**。本项目约定：
`class == "UnrealWindow"` 且 `title` 含 `《剑灵》`，**不可模糊搜索**。

实测在同一台机器上按标题枚举"剑灵"，得到 **3 个** 窗口：

| hwnd | class | title | 真身 |
|---|---|---|---|
| `1114802` | `UnrealWindow` | `《剑灵》` | ✅ **真正的游戏窗口** |
| `853834` | `HwndWrapper[剑灵小助手;...]` | `剑灵小助手 决战巅峰延迟: 27ms` | ❌ 第三方工具 |
| `200570` | `GDI+ Hook Window Class` | `GDI+ Window (剑灵小助手.exe)` | ❌ 第三方工具 |

**如果类名读不到，`_verify_target_window` 的复核就只能靠标题模糊匹配 ——
会绑到「剑灵小助手」这个第三方外挂/辅助工具的窗口上去。**
后果：读到的全是垃圾数据，且因为"绑定成功了"，排查方向会被完全带偏。

### 根因

**本机 DM 7.2607 的类名方法叫 `GetWindowClass`，不叫 `GetClassName`。**
代码里写死了 `GetClassName`。

实测 COM dispid 探测结果：

```
  --  GetClassName     None      <- 不存在
  OK  GetWindowClass   69        <- 真正的类名方法
  OK  GetWindowTitle   68
  OK  EnumWindow       61
  OK  FindWindow       162
```

### 修复

新增 `DmCore._window_class(hwnd)` 兼容层，依次尝试 `GetWindowClass` → `GetClassName`：

```python
for name in ("GetWindowClass", "GetClassName"):
    try:
        return str(self._call(name, self._target(hwnd)) or "")
    except E.DmMcpError as exc:
        last_exc = exc
```

接入点：`_verify_target_window()`（复核逻辑）+ `get_class_name()`（`dm_get_class_name` 工具）。

### 验证

```
hwnd 1114802 -> {'class_name': 'UnrealWindow', 'ok': True}          <- 游戏
hwnd 853834  -> {'class_name': 'HwndWrapper[剑灵小助手;...]', ...}   <- 被正确识别为异类
hwnd 200570  -> {'class_name': 'GDI+ Hook Window Class', ...}       <- 被正确识别为异类
```

`dm_auto_bind` 现在能**精确锁定** `hwnd 1114802`（真正的游戏窗口），不再有误绑风险。

## D4 — `--backend dll` 在本机不可用（P2）

### 现象

```
--backend dll -> DM_EXPORT_MISSING: dm.dll 中未找到导出 GetClassName
exports_found: {'DllRegisterServer', 'DllUnregisterServer',
                'DllGetClassObject', 'DllCanUnloadNow'}
```

### 结论

`dm.dll` 只导出 **4 个标准 COM 入口**，**没有任何扁平 C 函数导出**。
所以 dll 后端在本机（DM 7.2607）**根本走不通**：

| 后端 | 可用性 | 说明 |
|---|---|---|
| `com` | ✅ **唯一可用** | 走 `IDispatch` 晚期绑定，`dm.dmsoft` |
| `dll` | ❌ 不可用 | dm.dll 无扁平导出 |

**这不是代码 bug，是 DM 的发布形态决定的。** 已在文档中澄清，
避免后人浪费时间去调 `--backend dll`。

> 附带好处：`NOT_SUPPORTED` 错误码的 hint 里写着"可改用 --backend dll 重试" ——
> 这条建议在本机会误导人。已在 `02-工具参考与错误码.md` 中补充说明。

## 给团队的两条方法论要点

1. **"能捕获异常"是错觉，"别调用它"才是解药。**
   访问违例、栈溢出、`abort()` 这类错误，Python 层的 `try/except` 统统无效。
   对这类接口，唯一可靠的做法是**调用前做状态预检**。
   判断标准：问自己"这次调用失败时，我的进程还在不在？" —— 不在，就不能靠异常处理。

2. **未配置的状态必须当成一等公民来测。**
   本轮 3 个缺陷里有 2 个（D1/D2）只在"没配注册码"时出现 ——
   而"没配注册码"恰恰是**新人 clone 下来的默认状态**。
   我们之前所有测试都默认"注册码齐全"，所以一直没撞到。
   **默认状态 = 最该测的状态。**
