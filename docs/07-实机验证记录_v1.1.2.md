## 1. D5（P0）：地址必须传十六进制字符串，十进制会静默返回 0

### 现象

修好注册与盾之后（v1.1.1），自检 `[6] 真实读内存` 输出 `{"value": 0, "raw": 0}`，
而 `GetModuleBaseAddr` 正确返回 `0x140000000`。**读成功、但值恒为 0**。

### 定位

直接对 DM 做对照实验（同一窗口、同一地址、同一 type）：

```python
ReadInt(1114802, "0x140000000", 3)  # -> 12894362189  = 0x3_00905A4D，低 32 位 0x905A4D = "MZ"  ✅
ReadInt(1114802, "5368709120", 3)   # -> 0                                                      ❌
```

`ReadInt` 的第三个参数同为一个不存在的地址时，DM 会返回 0 并置 `GetLastError`；
但传**十进制字符串**时 `GetLastError` **保持 0** —— 这是一个纯粹的**静默失败**。

### 为什么这是最危险的一类 bug

- 没有异常、没有错误码、没有日志线索；
- 调用方看到的是"调用成功，值是 0"，会把 `0` 当成真实内存内容，
  进而错误地断定"游戏没在跑 / 偏移错了 / 盾没加载"，排查方向完全跑偏；
- 本项目 v1.1.1 之前**所有**读接口、写接口、分块读写的**每一处**都踩了这个坑。

### 修复

在 `core.py` 顶部新增单一出口函数，全项目统一使用，禁止各处手写 `str(addr)`：

```python
def addr_str(addr):
    """把地址转成 DM 能正确解析的十六进制字符串（"0x140000000"）。"""
    return hex(num(addr))
```

修改点（原 `str(...)` → `addr_str(...)`）：

| 位置 | 原代码 | 现代码 |
|---|---|---|
| `_read_float_like` | `str(addr)` | `addr_str(addr)` |
| `read_int` | `str(addr)` | `addr_str(addr)` |
| `read_string` | `str(addr)` | `addr_str(addr)` |
| `read_raw_bytes` | `str(base + off)` | `addr_str(base + off)` |
| `read_data(native)` | `str(addr)` | `addr_str(addr)` |
| `write_int/float/double/string` | `str(addr)` | `addr_str(addr)` |
| `write_raw_bytes` | `str(base + off)` | `addr_str(base + off)` |

> **`read_raw_bytes` 是漏网之鱼**：首轮修复只改了"显式出现 `str(addr)`"的 9 处，
> 是靠新增的 `tests_addr_format.py` 断言"每一次 ReadInt 调用的地址参数都以 `0x` 开头"
> 才把它抓出来的。这个例子说明：**修这类 bug 必须靠断言每次调用的实参，而不是靠 grep 搜索。**

### 回归测试

新增 `tests_addr_format.py`（离线，用假后端记录每一次调用的实参）：


## 2. D6（P0）：`VirtualAllocEx / VirtualProtectEx / VirtualFreeEx` 签名与 Windows API 不同

### 现象

`selftest --allow-write` 在 `[7] 真实写内存` 直接失败：

```
FAIL {"ok": false, "error": "DM_CALL_FAILED",
      "message": "IDispatch::Invoke(VirtualAllocEx) 失败",
      "detail": {"hresult": -2147352562, "excep": ""}}
```

### 定位：读 DM 自己的类型库

COM 晚期绑定失败时 `hresult=-2147352562`（`DISP_E_BADPARAMCOUNT`）说明**参数个数不对**。
与其猜，不如直接问 dm.dll —— 用 `IDispatch::GetTypeInfo` 读它的真实签名：

```python
o = win32com.client.Dispatch('dm.dmsoft')
ti = o._oleobj_.GetTypeInfo()
ta = ti.GetTypeAttr()
for i in range(ta.cFuncs):
    fd = ti.GetFuncDesc(i)
    names = ti.GetNames(fd.memid)
    if names and names[0].lower() in want:
        print(names, len(names) - 1)   # 方法名 + 每个参数名，共 cFuncs=444 个方法
```

**这是本次最有价值的工具**：`dm.dll` 的类型库里带着**每个方法的完整参数名与个数**，
是比任何网上文档都权威的一手事实来源。

结果：

```
VirtualAllocEx        (4)  hwnd | addr | size | type
VirtualProtectEx      (5)  hwnd | addr | size | type | old_protect
VirtualFreeEx         (2)  hwnd | addr
Reg                   (2)  code | Ver
ReadInt               (3)  hwnd | addr | type
WriteInt              (4)  hwnd | addr | type | v
ReadString            (4)  hwnd | addr | type | len
ReadDataAddr          (3)  hwnd | addr | len
FindInt               (5)  hwnd | addr_range | int_value_min | int_value_max | type
FindFloat             (4)  hwnd | addr_range | float_value_min | float_value_max
FindDouble            (4)  hwnd | addr_range | double_value_min | double_value_max
FindString            (4)  hwnd | addr_range | string_value | type
FindData              (3)  hwnd | addr_range | data
```

### 对照我们的实现

| 接口 | DM 真实签名 | 我们原来的调用 | 差异 |
|---|---|---|---|
| `VirtualAllocEx` | 4 参，**无 protect** | 5 参（多了 `protect`） | ❌ 个数不匹配 |
| `VirtualProtectEx` | 5 参，末位 `old_protect` | 5 参 | ✅ 个数对（语义需注意） |
| `VirtualFreeEx` | **仅 2 参** `(hwnd, addr)` | 4 参 `(hwnd,addr,size,type)` | ❌ 个数不匹配 |

### 修复

```python
# VirtualAllocEx(hwnd, addr, size, type) —— 4 参，没有 protect；type=1 为 64 位模式
def virtual_alloc_ex(self, size, addr=0, type=1, hwnd=None):
    ret = num(self._call("VirtualAllocEx", self._target(hwnd), int(addr), int(size), int(type)))

# VirtualProtectEx(hwnd, addr, size, type, old_protect) —— 末位传入新属性、返回旧属性
def virtual_protect_ex(self, addr, size, type=1, protect=0x40, hwnd=None):
    ret = num(self._call("VirtualProtectEx", self._target(hwnd), int(addr), int(size),
                         int(type), int(protect)))

# VirtualFreeEx(hwnd, addr) —— 只有 2 参，没有 size/type
def virtual_free_ex(self, addr, hwnd=None):
    ret = num(self._call("VirtualFreeEx", self._target(hwnd), int(addr)))
```

**`type` 默认值同时从 `0` 改为 `1`**：`0`=32 位模式、`1`=64 位模式。
剑灵是 64 位进程，用 `0` 申请到的是 32 位地址空间（`VirtualAllocEx` 返回 `0x3D05F6000`），
放不下 64 位指针测试值。这是第二个隐藏坑。

## 3. D7（P0）：`FindInt` 等的参数**语义**全错

### 现象

写回环通过后测试搜索，`FindData(范围, "4D 5A")` 恒返回空 ——
而模块基址第一个字节就是 `4D 5A`，且 `ReadInt` 已证实可读。

### 定位

对照类型库签名：

```python
# DM 真实签名
FindInt(hwnd, addr_range, int_value_min, int_value_max, type)
FindFloat(hwnd, addr_range, float_value_min, float_value_max)
FindString(hwnd, addr_range, string_value, type)
FindData(hwnd, addr_range, data)
```

我们原来的实现：

```python
def find_int(self, addr_range, values, type=0, step=1, hwnd=None):
    return self._find("FindInt", addr_range, values, (int(type), int(step)), hwnd=hwnd)
    #                                                     ^^^^ ^^^^^^^^^^^
    #  实际传给 DM: (hwnd, range, values, type, step)
    #  DM 期望的:   (hwnd, range, min,    max,  type)
```

**两个错误叠加**：

1. **`step` 被传到了 `int_value_max` 的位置**。`step` 默认 1，所以等于"搜索数值上界 = 1" ——
   只可能命中数值 0 或 1，其他值一律搜不到。调用方即使传了正确的 `value`，
   也会因为"上界 = 1"而搜不到任何东西。
2. **`type` 被传到了 `int_value_max` 之后的位置**（即 DM 的 `type` 位）——
   这次巧合地"对"了，因为默认都是 0。

更根本的是：`FindInt` **根本没有 `step` 参数**（需要步长要用 `FindIntEx`）。
这个字段是我们按"CE 搜索界面有步长"的直觉臆造的。

### 修复

```python
def find_int(self, addr_range, value_min, value_max=None, type=0, step=1, hwnd=None, ...):
    # FindInt 本体无 step；step != 1 时自动改用 FindIntEx（*Ex 变体才有 step）
    if step and int(step) != 1:
        return self.find_int_ex(addr_range, value_min, value_max, type=type, step=step, ...)
    return self._find("FindInt", addr_range,
                      [value_min, value_min if value_max is None else value_max, int(type)],
                      hwnd=hwnd)
```

同时补齐 `FindIntEx / FindFloatEx / FindDoubleEx / FindStringEx / FindDataEx`
（真实签名分别为在基础版末尾追加 `step, multi_thread, mode`）。

MCP 工具 schema 也同步改名与文档化：`values` → `value_min` / `value_max`，
并在描述里写明"`FindInt` 本体没有 step，`step!=1` 时服务自动改用 `FindIntEx`"。

## 4. D8（P1）：`Reg` 无法传附加码

`Reg` 的真实签名是 `Reg(code, Ver)` —— **必须 2 个参数**（`Ver` 官方即"附加码"）。
单参数会 `DM_CALL_FAILED`。

原实现：

```python
ret = self._be.call("Reg", code, "")     # 硬编码 ""，附加码永远传不进去
```

实测第 2 参传 附加码 / `7.2301` / `""` 返回值均为 1（DM 不校验其内容），
但按约定应传真实附加码 —— 填错虽不报错，却属配置不实，换机器/换版本时容易踩坑。

### 修复

- `DmCore.__init__(..., extra_code=None)`：新增 `self.extra_code`
- `reg(code, extra_code=None)`：`None` 时取实例配置
- `run_server.py`：新增 `resolve_credentials()`，优先级
  **`--reg-code/--extra-code` > 环境变量 > `dm_reg.txt` > `config.json`**
- `status()` 只回显 `reg_code_configured` / `extra_code_configured` **布尔值**，
  **绝不回显明文**（防止凭据经日志或响应泄露）

## 5. D9（外部限制，无法修复）：ACE 反作弊下 `Find*` 搜索不可用

> ⚠️ **这不是本项目代码的缺陷，是剑灵 ACE 反作弊的既定防护。**
> 记录下来是为了避免团队后续把大量时间浪费在"调搜索参数"上。

### 现象

读写全部正常（`ReadInt` / `WriteInt` / `VirtualAllocEx` 回环均通过），
但 `FindInt` / `FindFloat` / `FindDouble` / `FindString` / `FindData` 及全部 `*Ex` 变体返回空串。

### 决定性证据

同一窗口、同一地址、同一个值：

```
ReadInt(0x140000000)                        = 0x00905A4D   （MZ 头，读得到）✅
FindInt(范围=0x140000000-0x160000000, 值=9460301) -> 0 个                 ❌
FindData(范围=0x140000000-0x160000000, "4D 5A")  -> 89 个，但首个 = 0x1514279E1
                                                              （不等于 0x140000000）❌
FindInt(范围=0x00000000-0xFFFFFFFF, 值=0x5A4D)    -> 28 个，首个 = 0x049AA342
                                                              （也不是 0x140000000）❌
```

补充观察：搜索**极小范围**（如 `base ~ base+0x1000`）恒为空；把范围放大到
`0x140000000-0x160000000` 才会"有结果"，但返回的地址全是 `0x14F19xxxx`、`0x151427xxx`
这类**模块外/堆区**地址，且**从不包含**那个已被 `ReadInt` 证实存在的 `0x140000000`。

### 根因判定

ACE 对游戏模块做了**影子页（shadow page）保护**：

- **按地址直读**走驱动通道 → 拿到真实数据（`ReadInt` 正确返回 MZ 头）
- **遍历扫描**看到的是 ACE 改写的映像 → 真数据对扫描不可见，扫到的只是噪声

### 已尝试且**无效**的方案（供后续避免重复尝试）

| 方案 | 结果 |
|---|---|
| 盾模式：`memory` / `memory2` / `b3` / `b2` / 组合 | `ReadInt` 均正常，`FindData` 全部为空 |
| 绑定 display 属性：`normal` / `dx.public.memory` / `dx.public.memory\|dx.public.inject.super` | 同样为空 |
| `BindWindowEx(..., "dx.public.memory", 0)` | 绑定成功，搜索仍为空 |
| 范围写法：`0x..-0x..` / 十进制 / 无 `0x` 前缀 / 大写 `0X` / 逗号 / 单地址 | 均无效（且这些写法差异确实影响解析） |
| 范围放大到 `0x00000000-0xFFFFFFFF` 全空间 | 有结果，但**不含**已知存在的目标地址 |
| `FindDataEx/FindIntEx` 带 `multi_thread` / `mode` | 同上 |

### 对项目的影响与建议

- **不影响** `dm-mcp` 的核心定位：用户明确说明「dm 的 mcp 就是为了替代 x64dbg 的功能，读写用的」。
  **读写已实测全部可用**，D9 仅影响"搜索扫描"这一附加能力。
- 需要**搜索型**探查时，应改用**已知偏移 + 逐点读取**：
  用上层工程已维护的偏移表（模块基址 + 各级偏移）
  直接 `read_int` 沿指针链走，而不是全内存扫描。
  具体偏移数值属上层项目内容，本仓库不展开。
- `dm_find_*` 工具保留并在描述中标注该限制，避免后续误判为"工具坏了"。

## 7. 方法论沉淀（写给团队）

1. **`dm.dll` 的类型库是终极事实来源。**
   任何 COM 接口签名存疑时，不要查博客、不要猜，直接
   `IDispatch::GetTypeInfo()` 打印方法名与参数名（本版本共 444 个方法）。
   本次 D6/D7 两个 P0 都是靠这一步在几分钟内定位的。

2. **最危险的 bug 是"静默返回 0"，不是"报错"。**
   D5/D7 都不抛异常、`GetLastError` 也是 0。排查时应该用
   **"能读到的已知值"做对照**（模块基址的 MZ 头 `0x905A4D` 是天然金标准）。
   如果 `ReadInt(模块基址)` 不是 `0x...5A4D`，一定是链路出了问题，而不是"游戏没跑"。

3. **修"传参格式"类 bug，要断言"每次调用的实参"，不能只靠 grep。**
   D5 首轮按 grep 改了 9 处，`read_raw_bytes` 里的 `str(base + off)` 漏了；
   是新增的假后端断言"每个 ReadInt 的地址参数都以 `0x` 开头"才把它抓出来。

4. **先分清"我们的 bug"和"外部限制"。**
   D9 花的时间最值得警惕：现象是"工具坏了"，根因却在 ACE。
   判定方法：**用同一地址、同一值的 `ReadInt` 打对标** ——
   读得到而搜不到，就是外部限制，不必再调搜索参数。

5. **凭据不要回显。** `status()` 只回布尔值；日志只记"已提供/来源"。
