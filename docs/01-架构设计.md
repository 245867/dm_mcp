# 01 · 架构设计

## 1. 分层（沿用本机既有约定：宿主桥 + MCP 适配层）

本机既有逆向项目的 MCP 一律是两层结构（如 `x64dbg-mcp-server` 的“插件 REST 桥 + 独立 MCP 适配层”、`CE_MCP_Bridge`），dm-mcp 沿用同一思路，但把两层合并到同一进程内，避免多进程通信带来的脆弱性：

```
┌──────────────────────── dm-mcp 进程（必须 32 位） ─────────────────────────┐
│  server.py                                                                │
│    ├── MCP 适配层：stdio(JSON-RPC 2.0) ／ HTTP POST /mcp                   │
│    └── 宿主桥：HTTP GET/POST /api/<tool>（便于 PowerShell / Python 脚本直调）│
│                              │                                            │
│  tools.py   工具注册表：name / description / inputSchema / 前置条件        │
│                              │                                            │
│  core.py    DmCore：唯一持有 DM 状态（盾标记、绑定 hwnd、超时）+ 前置校验   │
│                              │                                            │
│  backend.py DllBackend(ctypes 直调导出)  ／ ComBackend(IDispatch 晚期绑定)  │
└──────────────────────────────┬───────────────────────────────────────────┘
                               │
                        dm.dll（x86，COM ProgID: dm.dmsoft）
                               │
                     DmGuard 内核级盾（driver）
                               │
                 64 位目标进程（如 BNSR.exe）内存
```

## 2. 模块职责

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `backend.py` | 把 dm.dll 抽象为 `call(name, *args)` | 双后端：`ComBackend` 用最小 IDispatch 晚期绑定（纯标准库，不依赖 pywin32/comtypes，返回值走 VARIANT 语义完整，为既有工程实测路径）；`DllBackend` 用 ctypes 直调 C 式导出（自带 PE 导出表解析，处理 `_ReadInt@12` 之类 stdcall 修饰与 32 位入栈宽度）；`auto` **先 com 后 dll**（dll 直调作为“免注册调用”兜底） |
| `hostenv.py` | 32 位宿主自举（入口第一步） | 探测本机 32 位 Python（优先级：`--python32` → `config.json.python32_path` → 环境变量 `DM_MCP_PYTHON32` → 项目内 `python32\python.exe` → 注册表 `PythonCore`（32 位视图）→ 常见安装目录 → `py -3-32`，**逐个真实执行** `sizeof(c_void_p)` 校验位数，不猜）；64 位宿主自动用找到的 32 位解释器重新拉起自身（`DM_MCP_RELAUNCHED=1` 重入保护，stdio 管道继承）；找不到则输出“获取/配置 32 位 Python”引导文案并 `exit(2)` |
| `core.py` | 生命周期、盾、绑定、读写、搜索、内存操作 | 所有内存类方法先 `_ensure_guard()`；状态（盾/绑定/超时）常驻保存，跨调用生效 |
| `tools.py` | 工具清单与分发 | 工具清单即 MCP `tools/list` 返回体；`REQUIRES` 表声明每个工具的前置条件；`WRITE_TOOLS` 标记中风险写接口 |
| `server.py` | 两个前端 | stdio：逐行 JSON-RPC，stdout 只放报文，日志进 stderr/文件；HTTP：`POST /mcp`（JSON-RPC，支持批量）+ `/api/<tool>`（REST）+ `/health`、`/status`、`/tools` |
| `errors.py` | 错误码与异常 | 服务层错误码稳定；DM 返回值与 `GetLastError` 原样随附，不做主观解释 |

## 3. 关键流程

### 3.1 启动与加载（先做宿主自举，再做默认绑定）

```
run_server.py
  → 宿主位数自举（hostenv.ensure_32bit_host，入口第一步）
        * 已是 32 位           → 继续
        * 64 位且找到 32 位解释器 → 用其重新拉起自身（子进程继承 stdin/stdout/stderr，父进程等待后以子进程返回码退出）
        * 64 位且找不到         → 打印“获取/配置 32 位 Python”引导文案 → sys.exit(2)（DM_MCP_NO_PYTHON32 / DM_MCP_RELAUNCH_FAILED）
  → DmCore.load()
        backend.create_backend(auto)          # 定位 dm.dll：参数 → DM_DLL/DM_PATH → 常见位置 → 注册表 dm.dmsoft
        SetPath(dm.dll 所在目录)
        Reg(reg_code)                         # 有注册码才调用；失败仅警告（registered=false）
        Ver()                                 # 版本
        DmGuard(1, "memory2") / DmGuard(1, "b3")   # 全部返回 1 才置 guard_loaded=true
  → mode=stdio: serve_stdio()    mode=http: serve_http()
```

### 3.2 内存读取为什么默认走“分块 ReadInt”

既有工程实测：DM 原生 `ReadDataAddr` 对 60 亿级大地址（如 `0x140000000+`）不稳定，常返回空串。因此 `dm_read_data` 默认按 `8/4/2/1` 字节宽度循环调用 `ReadInt`（`type=3/0/1/2`）拼接字节流，`native=true` 时才走原生接口。写入侧同理：`dm_write_data` → 分块 `WriteInt`。

### 3.3 盾（DmGuard）门禁

- 门禁点在 `core._ensure_guard()`：未加载盾 → 抛 `DM_GUARD_NOT_LOADED`，**调用不会下发到 DM**。
- 覆盖范围：`dm_read_*`、`dm_write_*`、`dm_find_*`、`dm_virtual_*`，以及 `dm_raw_call` 中名称以 `Read/Write/Find/Virtual` 开头的接口。
- `dm_guard(enable=false)` 只是置服务侧标记（DM 无卸盾接口），用于诊断。

### 3.4 线程与 COM 公寓（STA）

DM 为 STA 组件。stdio 模式所有调用天然在主线程；HTTP 模式刻意使用**单线程** `HTTPServer`（而非 `ThreadingHTTPServer`），保证 `CoInitializeEx` 与后续调用落在同一线程与公寓，避免跨公寓调用失败。

## 4. 状态与常驻语义

| 状态 | 存放位置 | 生命周期 |
|---|---|---|
| 盾是否已加载 | `DmCore._guard_loaded` | 进程内常驻 |
| 已绑定窗口 hwnd | `DmCore._hwnd` | 进程内常驻（也可每次调用显式传 `hwnd`） |
| DM 对象、屏蔽/超时等设置 | dm.dll 内部 | 进程内常驻 |

因此 HTTP 模式下“加载一次、长期服务”，正是常驻进程语义；stdio 模式下进程由 MCP 客户端托管，会话内同样持续存活。

## 5. 与既有工程的对应关系

| 既有工程结论 | 在 dm-mcp 中的落地 |
|---|---|
| DM 7.2607，Reg=1，DmGuard(memory2/b3)=1 | 默认盾模式 `["memory2","b3"]`；`Reg` 失败仅告警 |
| 读 64 位必须 `ReadInt type=3` | `dm_read_int` 默认 `type=3`，并在 schema 里写明语义 |
| 不可调用 `SetMemoryHwndAsProcessId(1)` | 该工具默认 `enable=0` 且返回体附警告 |
| 窗口绑定 `Class=UnrealWindow` + 标题含《剑灵》 | `config.json` / `--window-class` / `--window-title` 默认值 |
| 纯 `ReadProcessMemory` 被 ACE 拒绝，须走 DM 或 x64dbg 通道 | 本服务即 DM 通道；盾未加载一律拒绝，避免误判为“读不到” |
| DM 地址为 CE 风格表达式 | `addr` 统一为字符串，支持 `0x140000000` / `bnsr+0x1234567` / `[0x1234]+8`，由 DM 自行解析 |
| 32 位宿主 + 盾是访问 64 位目标的唯一组合 | `hostenv.py` 启动自举：64 位宿主自动改用 32 位解释器重新拉起自身，找不到则引导退出（不再静默以 64 位启动，避免“COM 后端返回 None”） |
| 窗口绑定沿用 `UnrealWindow` + 标题含《剑灵》 | 启动默认执行 `dm_auto_bind`（class/title/module 均有默认值），结果写入 `dm_status.auto_bind`，用户无需再手动 `dm_find_window` + `dm_bind_window` |
