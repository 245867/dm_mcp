# 04 · 常见问题（FAQ）

## Q1 启动即报 `DM_MCP_NOT_32BIT` / COM 后端返回 None / 读不到 64 位目标进程？

dm.dll 是 x86（32 位）组件，必须由 **32 位** 进程承载；64 位进程既无法 `CoCreateInstance` 32 位 in-proc COM（ProgID `dm.dmsoft`，表现为“创建失败 / 返回 None / HRESULT 报错”，即 *COM 后端不可用*），也无法 `LoadLibrary` 加载 x86 的 dm.dll。DM 又依赖内核级 `DmGuard` 访问 64 位目标进程，因此 **32 位宿主 + 盾是唯一可行组合**。

检查当前宿主位数：`python -c "import ctypes;print(ctypes.sizeof(ctypes.c_void_p)*8)"`，输出应为 `32`。

现在**不需要**手工换解释器了（v1.1 起 `run_server.py` 启动自检）：

1. **已是 32 位** → 直接继续启动；
2. **是 64 位且本机有 32 位 Python** → 自动用 32 位解释器**重新拉起自身**（stdio 管道继承，MCP 客户端无感），日志会打印 `检测到 64 位宿主，已自动改用 32 位解释器重新拉起自身：<exe>（来源：…）`；
3. **找不到 32 位 Python** → 打印引导文案并以返回码 `2` 退出（错误码 `DM_MCP_NO_PYTHON32`），**不会**带着 64 位宿主继续跑。

指定 32 位解释器（优先级由高到低）：`--python32 "D:\Python311-32\python.exe"` → `config.json` 的 `python32_path` → 环境变量 `DM_MCP_PYTHON32` → 项目内 `python32\python.exe` → 注册表 `PythonCore`（32 位视图）→ 常见安装目录 → `py -3-32`。每个候选都会被真实执行一次位数探测，不靠猜。

安装 32 位 Python（任选一种）：
- 官网 `Windows installer (32-bit)`（不要选 x86-64），安装时勾选 *Add python.exe to PATH*；
- 一行命令：`winget install --id Python.Python.3.11 --architecture x86 -e`；
- 免安装嵌入式包：解压出 `python.exe`，放到项目下的 `python32\` 目录即可被自动发现。

只想在 64 位下看引导信息（不重拉）：加 `--no-relaunch`。MCP 客户端里也可直接把 `command` 指向 32 位解释器绝对路径（双保险）。

## Q1b 哪些环节属于“已自动完成”，不用我手动调？

服务（`--mode stdio` / `--mode http`）启动顺序固定为：

```
宿主位数自检（必要时自动重拉为 32 位）
  → dm_load（SetPath → Reg → Ver → 加载盾 memory2/b3）
  → 启动默认绑定：dm_auto_bind（class=UnrealWindow + 标题含“剑灵” + 进程 bnsr.exe）
  → 起服务
```

因此正常情况下客户端只需 `dm_status` 确认 `host.bits=32`、`guard_loaded=true`、`bound_hwnd` 非空、`auto_bind.ok=true`，然后直接读内存即可。游戏**未启动**时服务照常启动，`auto_bind` 会给出 `error=DM_NO_TARGET` 与提示，等游戏起来后再调一次 `dm_auto_bind` 即可；不想要该默认行为时用 `--no-autobind`（或 `config.json` 的 `"auto_bind": false`）。

## Q2 报 `DM_DLL_NOT_FOUND`

按以下顺序提供路径即可（优先级从高到低）：
1. `--dm-path D:\xxx\dm.dll`
2. 环境变量 `DM_DLL` 或 `DM_PATH`（目录或文件均可）
3. `config.json` 的 `dm_path`
4. 自动探测：脚本同目录 / `dm\` / `bin\` / `lib\` / `D:\dm` / `D:\大漠` / `C:\dm`
5. 注册表 `HKCR\dm.dmsoft\CLSID` → `InprocServer32`（dm.dll 已注册时可直接反查到真实路径）

## Q3 `dll` 后端报 `DM_EXPORT_MISSING`，但 dm.dll 明明能用

部分 dm.dll 的导出名带 stdcall 修饰（如 `_ReadInt@12`）。本服务已内置 PE 导出表解析与修饰名匹配；若仍失败，说明该 dm.dll 只以 COM 方式对外（老版本常见），改用 `--backend com` 即可。

## Q4 `dm_guard` 失败（盾加载不成功）

- 未成功 `Reg`：注册码缺失/失效时，`memory2`、`b3` 等盾模式通常不可用。先 `dm_reg` 看是否返回 1。
- 权限不足：盾需要驱动级能力，请以**管理员身份**运行。
- 与安全软件冲突：ACE/SGuard 之类内核保护与盾可能互相干扰，出现蓝屏/拒绝时先停用其中之一。
- 只要 `dm_status.guard_loaded=false`，所有内存接口都会被拒绝（这是**有意设计**，避免把“盾没上”误判成“地址不对”）。

## Q5 为什么 `dm_read_data(native=true)` 常返回空？

DM 原生 `ReadDataAddr` 对 64 位大地址（`0x140000000` 以上）不稳定。**默认实现**改为按 8/4/2/1 字节宽度循环 `ReadInt`（`type=3/0/1/2`）拼接，实测更稳。写入侧同理走分块 `WriteInt`。

## Q6 读出来是 0 / 明显错误

排查顺序：
1. `dm_status` → `guard_loaded` 是否为 true；
2. 是否已绑定目标窗口（`bound_hwnd`），或调用时显式传了 `hwnd`；
3. `dm_set_asm_hwnd_as_process_id(1)` 是否生效；
4. 确认**没有**把 `dm_set_memory_hwnd_as_process_id` 置 1（置 1 会把 hwnd 当进程 ID，导致全失败）；
5. 读 64 位指针/HP 是否用了 `type=3`（默认 3，但显式传 0 会截断成 32 位）；
6. 模块基址是否最新（重启游戏后基址可能变化，需重新 `dm_get_module_base_addr`）。

## Q7 写接口安全吗？会不会改坏游戏？

写接口是真实写目标进程内存，属中风险且不可撤销。本服务做了三件事：返回体带 `risk` 标注；自检脚本默认只读（`--allow-write` 也只写自申请内存）；`dm_raw_call` 对 `Read/Write/Find/Virtual` 前缀接口强制校验盾状态。
建议流程：**先用只读接口验证地址链路 → 在临时申请的内存上验证写能力 → 再考虑写业务数据（且先备份原值）**。

## Q8 HTTP 端口被占用 / 想换端口

默认 `27043`。`--port 27999` 或写进 `config.json`。启动时若端口被占用会直接提示并退出（可能已有一个实例在跑）。

## Q9 能否多客户端并发？

可以，但**请求会被串行执行**：DM 是 STA 组件，HTTP 模式刻意用单线程服务器以保证调用落在同一线程/公寓。并发场景请把调用排队（每次调用都是毫秒级，实际够用）。

## Q10 服务会写日志吗？日志在哪？

`dm_mcp.log`（项目根目录），同时输出到 stderr。**stdio 模式下 stdout 只承载 JSON-RPC 报文**，日志绝不污染 stdout，否则会破坏 MCP 协议。

## Q11 想扩展尚未封装的 DM 接口

两种办法：
1. 直接用 `dm_raw_call`（`{"method":"SetWindowSize","args":[hwnd,800,600,1]}`），不用改代码；
2. 在 `dm_mcp/tools.py` 增加 `_tool(...)` 定义 + `HANDLERS` 条目，随后 `tools/list` 自动同步。

## Q12 第二步（BNSR HP 绘制）怎么接？

MCP 只负责稳定读写。绘制侧建议顺序：
1. 用 MCP 拿到模块基址，先复现上层的对象与名称解析（注意 FName chunk 上限 < 8192）；
2. 用 `dm_read_int(type=3)` 沿上层的多级指针链把目标数值读出来，再用一个已知值校验链路是否走通；
3. 匹配稳定性不够时，切换“以 UI 控件为主体”的遍历方案（控件自带屏幕坐标，天然与数值一一对应）；
4. 覆盖层 GUI（置顶/透明/鼠标穿透/可退出）由绘制侧实现，仅通过 MCP 取数。

## Q13 `dm_write_int` / `dm_write_string` 里 type 与 value 的顺序

服务按 DM 官方签名发出调用：`WriteInt(hwnd, addr, type, v)`、`WriteString(hwnd, addr, type, v)`（**type 在 v 之前**，与 `ReadInt(hwnd, addr, type)` 的写法保持同一顺序）。
工具层的入参是 `dm_write_int(addr, value, type=0)`，由服务重排成原生顺序，调用方无需关心顺序问题。

验证/排错方法：
1. 跑 `自检.bat`（写测试会“在自申请内存上写魔数 → 读回比对”），不一致即说明该 dm 版本的顺序或 type 语义与预期不同；
2. 若确实不一致，用 `dm_raw_call` 直接试两种顺序定位：
   - `{"method":"WriteInt","args":[hwnd, addr, 3, "404102"]}`
   - `{"method":"WriteInt","args":[hwnd, addr, "404102", 3]}`
   谁能让随后的 `dm_read_int(addr, type=3)` 读回 404102，就以谁为准（并在 `core.py` 对应位置同步）。

## Q14 注册码放哪里最安全？几种来源的优先级？

> 📌 **想一次性配好、以后不用管，直接看 [Q23 怎么设置才能"一劳永逸"](#q23-怎么设置才能一劳永逸)。**
> 本条目只讲优先级规则。

**优先级（从高到低）**：

1. 命令行：`python run_server.py --mode http --reg-code "xxxx" --extra-code "你的附加码"`
2. 环境变量：`set DM_REG_CODE=xxxx` / `set DM_EXTRA_CODE=你的附加码`（亦支持 `DM_MCP_REG_CODE`、`DM_MCP_EXTRA_CODE`）
3. **`dm_reg.txt`（推荐）**：`reg_code=xxxx` / `extra_code=你的附加码`
4. `config.json` 的 `reg_code` / `extra_code` 字段

为什么推荐 `dm_reg.txt` 而不是 `config.json`：两者都是明文落盘、都已 `.gitignore`，
但 `dm_reg.txt` 是**专一的凭据文件**，语义更清晰（一眼知道"这个文件里只有秘密"），
且 `setup_once.py` 会自动生成并校验权限；`config.json` 混着业务配置，
容易被随手复制/分享出去。

注意：启动日志只会打印“已提供（来源：…）”或“未提供”，**不会打印凭据本身**；
`dm_status` 也只回显 `reg_code_configured` / `extra_code_configured` 布尔值。

### 关于附加码（`Reg` 的第 2 个参数）

DM 的 `Reg` 是**双参数**接口：`Reg(注册码, 附加码)`，只传 1 个参数会 `DM_CALL_FAILED`。

实测（DM 7.2607 + COM）第 2 参传 `附加码` / `"7.2301"` / `""` 返回值**均为 1** ——
即 DM **不校验**其内容。但按官方约定应传注册时填写的附加码，
填错虽不报错，却属配置不实，换机器/换版本时容易踩坑。所以服务会如实传你配置的值。

未提供注册码时服务仍可启动（`Reg` 不会被调用），但 `DmGuard` / `BindWindow` 会被
**主动拒绝**（`DM_NOT_REGISTERED`）—— 因为未注册时调用它们会触发**进程级崩溃**。

## Q15 为什么 `dm_auto_bind` 有时“明明游戏开着却找不到”？

`dm_auto_bind` 对**自动找到的候选窗口**会做一次严格复核：

- `GetClassName(hwnd)` 必须**完全等于** `window_class`（默认 `UnrealWindow`，大小写敏感）；
- `GetWindowTitle(hwnd)` 必须**包含** `window_title`（默认 `剑灵`）。

复核不通过就继续试下一个候选，全部失败才返回 `DM_NO_TARGET`。
看返回体的 `steps[]` 即可知道每个候选是“没找到”还是“找到了但复核失败”：

```json
"steps": [
  {"try": "FindWindow(class=UnrealWindow, title=剑灵)", "ok": false, "hwnd": 0},
  {"try": "FindWindowByProcess(process=bnsr.exe, title='')", "ok": false, "hwnd": 3210992,
   "verify": "标题不含关键字：期望含 '剑灵'，实际 'Unreal Engine'"}
]
```

上例说明：进程找到了，但那个窗口是引擎的调试/启动窗口，标题里没有“剑灵”，
所以被正确拒绝了 —— 这正是复核要挡掉的误绑。

若你确认某个 hwnd 就是目标，可**显式**传参跳过复核：
`dm_auto_bind(hwnd="0x602F0")` 或 `dm_bind_window(hwnd="0x602F0")`。

## Q16 HTTP 接口返回 400 / 413 是什么意思？

| 状态码 | 响应体 `error` | 含义 |
|---|---|---|
| `200` | （无 `error`） | 执行成功 |
| `200` | 各类 `DM_*` | **工具级业务错误**（如未加载盾）。故意用 200，这样脚本客户端能直接读到结构化错误体，而不会被 `urlopen` 抛 `HTTPError` 打断 |
| `400` | `DM_UNKNOWN_TOOL` | 工具名不存在（调用方用错接口）；可先 `GET /tools` 取准确名称 |
| `401` | `UNAUTHORIZED` | 配置了 `token` 但未提供或不匹配 |
| `404` | `NOT_FOUND` | 路径不存在 |
| `413` | `REQUEST_TOO_LARGE` | 请求体超过 1 MiB 上限（单线程服务保护，正常工具入参远小于此） |

## Q17 没配注册码会怎样？为什么服务"拒绝绑定"而不是报个错？

**先说结论**：没配注册码时，服务**仍可正常启动**，但会**主动拒绝**加载盾与绑定窗口，
返回 `DM_NOT_REGISTERED`。这是**保护行为，不是故障**。

### 为什么必须主动拒绝

实测（DM 7.2607，2026-09-20）：**未注册状态下**调用以下接口会触发
`access violation reading 0x0` —— 这是 **Windows 访问违例，进程直接崩溃**：

| 接口 | 未注册时的后果 |
|---|---|
| `DmGuard`（加载盾） | 💥 进程崩溃 |
| `BindWindow` / `BindWindowEx`（绑定窗口） | 💥 进程崩溃 |

**关键点：这类崩溃 `try/except` 兜不住** —— 进程已经没了，异常处理代码根本没机会跑。
如果放任调用，结果是"客户端发一个请求，整个 MCP 服务消失，且没有任何可读错误"。

所以正确做法不是"捕获异常"（来不及），而是**调用前预检、根本不调用**。

### 你会看到什么

| 调用 | 返回 |
|---|---|
| `dm_load` | 正常返回；`guard_loaded:false`，`guard_detail` 标 `skipped-unregistered` |
| `dm_guard` | `DM_NOT_REGISTERED` + hint（提示配置凭据） |
| `dm_bind_window` | `DM_NOT_REGISTERED` + hint |
| `dm_auto_bind` | `ok:false, error:DM_NOT_REGISTERED`，**但仍会报出已找到的 hwnd**（定位能力不受影响） |

### 怎么解决

任选其一提供注册码，然后**重启服务**：

```
环境变量 DM_REG_CODE        （推荐，不落盘）
环境变量 DM_MCP_REG_CODE
<exe/项目目录>/dm_reg.txt
config.json 的 reg_code 字段
```

配置方式详见 [Q14](#q14-注册码放哪里最安全三种来源的优先级)。

## Q18 `--backend dll` 为什么报"未找到导出"？

**因为本机 `dm.dll` 根本没有扁平 C 导出。**

实测（DM 7.2607）导出表只有 4 个标准 COM 入口：

```
DllGetClassObject / DllCanUnloadNow / DllRegisterServer / DllUnregisterServer
```

| 后端 | 可用性 | 说明 |
|---|---|---|
| `com` | ✅ **唯一可用** | 走 `IDispatch` 晚期绑定（ProgID `dm.dmsoft`），本机实际使用的就是它 |
| `dll` | ❌ 不可用 | dm.dll 不提供扁平 C 函数，必然 `DM_EXPORT_MISSING` |

**结论：别在 `--backend dll` 上浪费时间，保持默认 `auto`（会选中 `com`）即可。**

> 配套修正：`DM_NOT_SUPPORTED` 的 hint 曾建议"改用 --backend dll 重试"，
> 这条建议在本机是误导性的 —— 现在你会看到 `dm_get_class_name` 已自带
> `GetWindowClass`/`GetClassName` 兼容层，多数情况下根本不会触发该错误。

## Q19 为什么 `dm_get_class_name` 曾经报 `DM_NOT_SUPPORTED`？

**命名差异**：本机 DM 7.2607 的类名方法叫 **`GetWindowClass`**，不叫 `GetClassName`。

这个坑很阴险，因为**类名校验是防止误绑的最后一道闸门**。实测同机按标题搜"剑灵"能搜出 3 个窗口：

| class | title | 真身 |
|---|---|---|
| `UnrealWindow` | `《剑灵》` | ✅ 真正的游戏 |
| `HwndWrapper[剑灵小助手;...]` | `剑灵小助手 ...` | ❌ 第三方工具 |
| `GDI+ Hook Window Class` | `GDI+ Window (剑灵小助手.exe)` | ❌ 第三方工具 |

类名读不到 → 只能靠标题模糊匹配 → **会绑到「剑灵小助手」上去**，读到的全是垃圾数据，
而且因为"绑定成功了"，排查方向会被完全带偏。

**现已修复**：`dm_get_class_name` 与 `dm_auto_bind` 的复核逻辑均自动尝试
`GetWindowClass` → `GetClassName`，无需你手动处理。

## Q20 读内存"成功"但值恒为 0 —— 最危险的一个坑

**症状**：`dm_read_int` 不报错、`dm_get_last_error` 返回 0，但 `value` 永远是 `0`。

**根因**：DM 的地址类接口**只认十六进制字符串**。传十进制字符串时 DM 不报错、
也不置 `GetLastError`，而是**静默返回 0**：

```
ReadInt(hwnd, "0x140000000", 3)  -> 12894362189   # 低 32 位 0x905A4D = "MZ" ✅
ReadInt(hwnd, "5368709120", 3)   -> 0             # 静默返回 0 ❌
```

**为什么它最危险**：没有任何异常或错误码，调用方会把 `0` 当成真实内存内容，
进而错误地断定"游戏没跑 / 偏移错了 / 盾没加载"，排查方向完全跑偏。

**现已修复**：`core.py` 统一走 `addr_str()`（输出 `"0x..."`），
所有读/写/分块读写/虚拟内存接口均不再出现 `str(addr)`。
并新增 `tests_addr_format.py` 用假后端断言"每次调用的地址参数都以 `0x` 开头"，
防止此类回归（该测试当初还抓出了 `read_raw_bytes` 里的漏网之鱼）。

**自查金标准**：`ReadInt(bnsr.exe 模块基址, type=0)` 必须得到 `0x…5A4D`（MZ 头）。
若不为该值，一定是链路问题，而不是"游戏没跑"。

## Q21 `dm_virtual_alloc_ex` / `dm_virtual_free_ex` 报 `DM_CALL_FAILED`（IDispatch::Invoke 失败）

**根因**：DM 的同名接口签名与 Windows API **不一样**，按直觉传参会因**参数个数不匹配**而失败
（`hresult = -2147352562` = `DISP_E_BADPARAMCOUNT`）。

以 dm.dll 自带类型库为准：

| 接口 | DM 真实签名 | 容易犯的错 |
|---|---|---|
| `VirtualAllocEx` | `(hwnd, addr, size, type)` **4 参，无 protect** | 按 Win32 补 `protect` → 5 参，失败 |
| `VirtualProtectEx` | `(hwnd, addr, size, type, old_protect)` | 个数对，但末位语义是"旧属性" |
| `VirtualFreeEx` | `(hwnd, addr)` **仅 2 参** | 按 Win32 传 `size`+`type` → 4 参，失败 |

**`type` 该怎么填**：`0`=32 位模式、`1`=64 位模式。
**剑灵是 64 位进程，必须用 `1`** —— 用 `0` 会申请到 32 位地址空间
（返回 `0x3D05F6000` 这类地址），放不下 64 位指针测试值。服务默认已改为 `1`。

**现已修复**：三个接口的签名与默认值全部按类型库对齐；
`dm_virtual_free_ex` 不再接受 `size`/`type` 参数。

**排查手法**：遇到 `IDispatch::Invoke` 失败时，直接问 dm.dll 要签名，比查任何文档都准：

```python
import win32com.client
o = win32com.client.Dispatch('dm.dmsoft')
ti = o._oleobj_.GetTypeInfo(); ta = ti.GetTypeAttr()
for i in range(ta.cFuncs):                       # 本版本 444 个方法
    names = ti.GetNames(ti.GetFuncDesc(i).memid)
    if names and names[0].lower() in ('virtualfreeex','findint'):
        print(names, len(names) - 1)              # 方法名 + 每个参数名 + 参数个数
```

## Q22 `dm_find_int` / `dm_find_data` 一直搜不到东西

**先分清是"我们的 bug"还是"外部限制"**——两者的处理方式完全不同。

### 情况一：参数用法变了（v1.1.2 起）

`FindInt` 的真实签名是 `(hwnd, addr_range, int_value_min, int_value_max, type)`。
**它没有 `step` 参数**（要步长得用 `FindIntEx`）。因此工具 schema 已改名：

| 旧参数名 | 新参数名 | 说明 |
|---|---|---|
| `values` | `value_min` | 数值下界 |
| — | `value_max` | 数值上界；**省略时等于 `value_min`（精确匹配）** |
| `step` | `step`（保留） | `!= 1` 时服务**自动改用** `FindIntEx`，你不用自己换工具 |

早期版本把 `step` 传到了 `value_max` 的位置，等于把"搜索上界"设成了 `1`，
导致除 0/1 之外的值一律搜不到。已修复。

各 Find 系列的真实签名（含是否有 `step`）：

```
FindInt(hwnd, range, min, max, type)                无 step
FindFloat/FindDouble(hwnd, range, min, max)         无 step
FindString(hwnd, range, value, type)                无 step
FindData(hwnd, range, data)                         无 step
*Ex 变体 = 基础版 + (step, multi_thread, mode)
```

### 情况二：ACE 反作弊导致搜索不可用（**无法修复**）

**剑灵（BNSR.exe）在 ACE 保护下，`Find*` 全系列返回空，但读写完全正常。**
这不是本项目的缺陷。决定性证据（同一地址、同一个值）：

```
ReadInt(0x140000000)                          = 0x00905A4D   ✅ 读得到（MZ 头）
FindInt(0x140000000-0x160000000, 9460301)     -> 0 个         ❌
FindData(0x140000000-0x160000000, "4D 5A")    -> 89 个，但首个 = 0x1514279E1
                                                 （不等于 0x140000000）❌
```

搜到的地址全是 `0x14F19xxxx` / `0x151427xxx` 这类模块外/堆区地址，
且**从不包含**那个已被 `ReadInt` 证实在 `0x140000000` 的 MZ 头。
根因是 ACE 做了**影子页（shadow page）保护**：按地址直读走驱动通道拿到真数据，
但遍历扫描看到的是被改写的映像。

已试过且**无效**（不必重复尝试）：`memory`/`memory2`/`b3`/`b2` 各种盾模式、
`dx.public.memory` 绑定属性、`BindWindowEx`、`FindDataEx` 带 `multi_thread`/`mode`、
各种地址范围写法、放大到 `0x00000000-0xFFFFFFFF` 全空间。

**建议**：需要定位数据时改用**"已知偏移 + 逐点读取"**：
用上层工程已维护的偏移表（模块基址 + 各级偏移）
直接 `dm_read_int` 沿指针链走，而不是全内存扫描。
具体的偏移数值属于上层项目内容，本仓库不展开。
`dm_find_*` 工具保留但受此限制，遇到返回空**不必怀疑工具坏了**。

## Q23 怎么设置才能"一劳永逸"？

DM 需要三样东西才能在每次启动时都凑齐：**注册码+附加码**、**32 位宿主**、**管理员权限**。
项目提供了 `setup_once.py` 一次性固化：

```bash
# 1) 只体检，不改任何文件（推荐先跑）
python setup_once.py --check

# 2) 写入凭据 + 32 位宿主路径 + 生成管理员快捷方式
python setup_once.py --apply --reg-code <你的注册码> --extra-code <你的附加码>

# 3) 回滚
python setup_once.py --revert
```

它会做四件事：

1. **凭据落盘到 `dm_reg.txt`**（已 gitignore，读盘即生效）
2. **`python32_path` 写进 `config.json`**（不再靠每次自动探测猜）
3. **生成「dm-mcp HTTP 服务（管理员）.lnk」**——双击自动弹 UAC 提权
4. **校验 `.gitignore` 确实覆盖了 `dm_reg.txt` 与 `config.json`**

### 凭据该放哪：四种方案对比

| 方案 | 持久 | 对已运行进程生效 | 污染系统 | 说明 |
|---|---|---|---|---|
| 系统环境变量 | ✅ | ❌ 需重启宿主进程 | 是 | 对 MCP 客户端拉起的场景尤其麻烦 |
| `config.json` | ✅ | ✅ | 否 | 明文落盘；已 gitignore |
| **`dm_reg.txt`（推荐）** | ✅ | ✅ | 否 | 已 gitignore、读盘即生效 |
| 管理员计划任务 | ✅ | ✅ | 是(轻) | 适合开机自启 |

`dm_reg.txt` 由 `run_server.py` **每次启动时读取**，改完重启服务即生效，
不像环境变量那样必须重启整个宿主进程。文件格式：

```
# 每行 键=值，# 开头为注释
reg_code=<你的注册码>
extra_code=<你的附加码>
```

### 解析优先级（高 → 低）

```
--reg-code / --extra-code 命令行
  > 环境变量 DM_REG_CODE / DM_EXTRA_CODE
    > dm_reg.txt
      > config.json 的 reg_code / extra_code
```

### 关于"管理员权限"

DM 的驱动级通道（`DmGuard`）需要提权，**这不是可选项**。
两种持久化做法：

- **单机自用（推荐）**：用 `setup_once.py --apply` 生成的
  「dm-mcp HTTP 服务（管理员）.lnk」，双击即自动提权，不用记着右键。
- **需要开机自启 / 无 UAC 弹窗**：用计划任务，勾选"使用最高权限运行"：

  ```bat
  schtasks /Create /TN "dm-mcp" /SC ONLOGON /RL HIGHEST ^
    /TR "\"C:\...\Python311-32\python.exe\" \"<项目根>\run_server.py\" --mode http --port 27043"
  ```

### 安全提醒

- 凭据**绝不会**出现在日志或 `dm_status` 里 —— 后者只回显
  `reg_code_configured` / `extra_code_configured` 两个**布尔值**。
- `dm_reg.txt`、`config.json` 均已在 `.gitignore` 中；
  提交前请确认 `git status` 看不到它们。
- 记忆点：**程序文件可以进 git，凭据文件不行。** 换机器时凭据要重新配置。

## Q24 HTTP 服务报 `LookupError: unknown encoding: idna` 起不来

**根因**：`HTTPServer.server_bind()` 默认会调 `socket.getfqdn(host)` 做反向解析，
该调用在部分解释器（实测 **Python 3.11.0b5** 这个 beta 版）上会因 idna 编解码器缺失而抛
`LookupError: unknown encoding: idna`。

**为什么难排查**：异常发生在 `HTTPServer.__init__` 里，
看起来像"端口占用 / 权限不足"，与网络其实毫无关系。

**现已修复**：`serve_http` 改用内建的 `_Server` 子类，其 `server_bind()` 跳过
`getfqdn()` 只做必要的 bind（`server_name` 仅用于 `Host` 头与日志，不影响功能）。
